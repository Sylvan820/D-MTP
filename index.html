DMTP：让预训练 MTP 为并行 Draft 开个好头

Piggy Shen · 2026 年 10 月 · 技术博客

投机解码已成为大模型推理基础设施的重要组成部分。DFlash 展示了并行预测多个候选的潜力，DeepSeek 也在生产服务中采用 DSpark，并报告了相对 MTP-1 的收益。然而，在 GLM、Qwen 等原生 MTP 训练充分的模型及部分对话场景中，DFlash 相比 MTP 并不总有显著优势。

我们的评测以及与 Domino 作者 Jianuo Huang 的讨论，揭示了两者的互补性：原生 MTP 的首 token 接受率更高，在 OOD 场景下尤其明显；DFlash 则能并行生成更长的续写。这为结合预训练首位能力与并行预测提供了直接动机。

针对DFlash类模型在block内后续位置接受率逐渐衰减的问题，已有多种改进方案。我们关注的是另一个问题：能不能先把第一个draft token的接受率提上去？ 在前缀验证下，首位被拒绝，后面的候选就无法在本轮提交。DMTP从预训练MTP的首位预测出发，再把它的hidden传给DFlash，帮助后续并行续写。

我们提出 DMTP：由预训练 MTP 生成第一个候选，再由 DFlash 并行生成后续候选。本文选择 MTP 式词元与隐藏状态融合作为主方法，将预测 T1 的 MTP 隐藏状态与 T1 词嵌入分别归一化、拼接投影，在 T1 输入位置连接预训练表示与并行续写。

核心思路： 让 MTP 为生成开个好头，让 DFlash 并行完成续写。两者既共享候选 token，也通过预测表示建立联系，而不必替换各自的主干。

核心观察

  • 原生 MTP 的首位优势值得复用。 在相同 Target 和输入下，我们观察到 MTP 的首 token 接受率高于 DFlash。因此，我们让 MTP 生成 T1，再由 DFlash 并行预测后六个候选。
  • 通过 hidden，把 MTP 的预训练能力带给 DFlash。 我们不只让 MTP 生成 T1，还把预测它时的 hidden 与 T1 的词嵌入融合。这样，DFlash 在续写时既能看到具体的候选，也能利用 MTP 在预训练中学到的特征，帮助后续 token 的并行预测。
  • 组合后的收益体现在完整生成中，也能与已有优化结合。 我们在六类任务上获得了 9.25%～19.56% 的接受长度提升；在 B32 的四类任务评测中，端到端吞吐提高了 17.10%～23.75%，均以 DFlash 为基线。DMTP 改进的是两者的协作方式，与 MTP、DFlash 各自的优化工作正交：更强的预测器、训练方法、候选选择策略和推理 kernel，都可以继续结合到这一框架中。

1. 首位接受率与并行 Draft

图1比较同一 Target 模型上的 DFlash 与原生 MTP。DFlash 使用混合任务数据训练，训练长度为 32K；MTP 使用同一 Target 自带的预训练权重。

两组采用相同的Qwen3.6-35B-A3B target和输入集合，覆盖Code、Math、MT-Bench、Agent、SWE、Long-horizon六类负载。DMTP组合只用MTP生成T1，后续六个候选由DFlash并行生成。

图 1：Qwen3.6-35B-A3B 在六类任务上的首 token 接受率，生成温度为 1。

Code 上，DFlash 与 MTP 的首位接受率分别为 71.00% 和 82.32%。

我们认为，大规模预训练是 MTP 首位优势的重要来源。 原生 MTP 随 Target 一起训练，接触的数据远多于我们单独训练的 DFlash draft。这让我们更倾向于保留它已经学到的首位预测能力，而不是重新训练一个替代模块。

2. DMTP：第一步用 MTP，后六步交给 DFlash

最直接的分工是：

MTP：生成 T1
DFlash：以 T1 为条件，一次生成 T2～T7
Target：验证七个候选，提交接受前缀与修正/bonus

图 2：原版 DFlash（上）与 DMTP（下）。DMTP 将预测 T1 的 MTP hidden 与 T1 词嵌入融合，再并行预测 T2～T7，保留原 Target context → KV 路径。T1 词嵌入来自 token 查表。

我们选择这个分工，主要考虑了三点。

保留首位能力。 我们冻结原生 MTP，保留其预训练的首位预测，只训练后续的并行 draft。

缩短预测距离。 给定 T1 后，T2 成为新 anchor 后的第一个未知 token，DFlash 以此为起点并行续写。

传递预训练特征。 除了 T1，我们还传入预测它时的 MTP hidden，让 DFlash 利用这些特征预测后续 token。

单步 MTP 预测

我们只用 MTP 生成 T1，以控制串行 draft 开销。更多 MTP 候选需要逐步前向与选词，而后六个候选可由 DFlash 一次并行生成。

3. MTP 表示的注入方式

我们采用 MTP 式词元与隐藏状态融合，并通过消融比较不同的表示注入方式。

设 A=xaA = x_aA=xa​ 是 Target 已经输出、但尚未处理的 pending token。Target context 截止 xa−1x_{a-1}xa−1​。MTP 读取上一位置的 Target hidden 与 AAA，得到用于预测 T1=xa+1T_1 = x_{a+1}T1​=xa+1​ 的表示。不需要 Target 处理 AAA 或 T1T_1T1​ 后的 hidden。

融合使用的就是预测 T1 时的 MTP hidden，不是消费 T1 之后的下一份 hidden：

e~T1=Wf[RMS⁡e(eT1);RMS⁡m(hMTP)].\widetilde{\mathbf e}_{T_1}=W_f\left[\operatorname{RMS}_e(\mathbf e_{T_1});\operatorname{RMS}_m(\mathbf h_{\mathrm{MTP}})\right].eT1​​=Wf​[RMSe​(eT1​​);RMSm​(hMTP​)].

两路 2048 维特征独立使用可学习 RMSNorm，再经 4096→2048 线性投影。输入采用 [T1,MASK×6]，只用融合结果替换 T1 的 embedding；六个 MASK 的 embedding 与原预测头保持不变，Target context 继续走原 FC→KV 路径，不增加 MTP KV 槽位。

MTP 式融合的设计

我们借鉴原生 MTP 的归一化与拼接投影结构，融合参数单独训练。E(T1) 指定候选 token，MTP hidden 提供预测特征，六个 MASK 通过 attention 读取融合后的 T1。

改动集中在 T1 的输入位置，历史特征、Target context 路径、DFlash 主干和候选预算保持不变。

单 Anchor 条件输入

一个 Anchor，七个候选。 以 MTP 提出的 T1 为唯一 anchor，DFlash 并行预测 T2～T7。T1 仍可能被拒绝，送去验证的七个候选是 T1～T7。

MTP 仍然消费 A，产生 T1 及预测它的 hidden；DFlash 只接收融合后的 T1 和六个 MASK。Target context 截止 A 之前，不需要额外执行 Target 前向。

双 Anchor 指在 MASK 前同时保留原本的 anchor A 和 MTP 提出的 T1。 输入为 [A,T1,MASK×6]，相比单 anchor 的 [T1,MASK×6]，额外提供 E(A)，让后续 MASK 通过 attention 更直接地读取原本 anchor 的词嵌入信息。A 已经输出，不属于本轮新增候选。

我们选择效果接近、改动更少的单 Anchor：将原版 anchor 换成 T1，保留单 anchor 加 MASK 的布局。MASK 的 embedding、并行预测与原输出头结构不变，便于从已有 DFlash 继续微调。

图3a：七个输入槽位、七个候选。T1由MTP生成，T2～T7由DFlash生成。已知T1槽位不计算draft预测loss。

消融设计

  • 原始 DFlash。 单锚点外部基线，输入为 [A,MASK×7]，由 DFlash 提出全部七个候选。
  • 仅使用候选词元的单锚点。 [T1,MASK×6]，不额外注入 MTP 隐藏状态；仍使用原目标模型的隐藏状态上下文。
  • 隐藏状态残差（首个候选位置）。 MTP 隐藏状态经低秩网络得到残差，只加到 T1 词嵌入，六个掩码输入保持不变。
  • MTP 式词元与隐藏状态融合（主方法）。 MTP 隐藏状态与 E(T1) 分别归一化、拼接投影，只替换 T1 词嵌入。

与现有 Draft 方法的兼容性

我们保留 DFlash 主干、输出头与 Target context 接口。配置匹配时，可从已有 DFlash 权重继续微调，新增 T1 融合模块，使用 [T1,MASK×6] 监督后六个预测位置；Target 与 MTP 保持冻结。

这一接口与 MTP、DFlash 各自的优化正交，可以结合更强的预测器、训练方法、path selector 和推理 kernel。

为什么保留预训练 MTP

我们也尝试过将 MTP layer 直接用于 DFlash 式并行预测，但观察到首位表现受到影响，收敛收益也有限。这让我们选择先冻结预训练 MTP，把它的首位能力保留下来，再围绕 T1 训练并行续写。

4. DMTP 训练流程

我们使用 Qwen3.6-35B-A3B，训练长度为 32K，数据规模约 25 万条，大部分来自 Agent 和 Long-horizon 场景。MT-Bench 属于训练分布之外的 OOD 评测，用于观察模型的跨场景泛化表现。

训练分为三步：

  1. 提取冻结特征。 Target 处理训练序列；在每个 block 边界，MTP 读取 A 与上一位置的 Target hidden，得到预测 T1 的表示。DFlash context 只使用 A 之前的 Target 特征。
  2. 构造 Draft 输入。 使用 [T1,MASK×6]，其中 T1 取自训练数据。E(T1) 与预测 T1 的 MTP hidden 分别归一化、拼接投影，替换 T1 embedding，六个 MASK 不变。
  3. 优化后续预测。 DFlash 沿用原位置衰减 CE，学习 T2～T7。Target 与 MTP 冻结，只更新 DFlash 与 T1 融合模块；已知 T1 输入槽位不计算 draft 预测 loss。

训练时我们使用 GT T1，推理时换成 MTP 实际生成的 T1，这部分仍有训推差异。两边使用的 hidden 则保持相同的时序：都取预测 T1 时的 MTP 表示，而不是消费 T1 之后的 hidden。

5. 推理流程：先 MTP，再 DFlash

每一轮生成都按图 2 的顺序执行：

  1. MTP 生成 T1。 读取已有的 Target hidden，消费 pending token A，保留选出的 T1 以及预测它时的 MTP hidden。
  2. DFlash 预测 T2～T7。 构造 [T1,MASK×6]，融合 E(T1) 与预测它的 MTP hidden，只替换 T1 embedding，再运行一次并行 DFlash 前向。
  3. Target 统一验证。 一起验证 T1～T7，提交接受前缀及修正/bonus token，再进入下一轮。

我们在本文实验中统一使用 target-only 验证。 根据 Target 的采样结果逐 token 检验候选，接受连续匹配的前缀。Rejection sampling 和 block verify 暂未接入，我们会在后续比较它们对接受长度和吞吐的影响。

运行时分别维护 MTP 与 DFlash 状态，只提交接受的历史，回退被拒绝候选产生的临时状态。

新增计算包括一次 MTP 前向、首位 LM head，以及两路归一化和一次 T1 融合投影。Target context 路径保持不变，DFlash block 使用 T1 与六个 MASK，共七个输入槽位。

接下来，我们重点优化状态更新、执行调度和 CUDA Graph 覆盖，减少 MTP 与 DFlash 之间的衔接开销。

6. 推理实现与系统优化

我们保留七个候选的预算和 Target 原有的验证规则，重点优化 MTP 状态推进与 T1 准备阶段。

6.1 一轮执行：预测与状态推进分开

虚线框表示 T1 head、embedding 与融合的组合 CUDA Graph，虚线箭头连接相邻两轮。

Prefill 初始化三侧状态。稳态轮次开始时，我们从缓存的 MTP hidden 选出 T1，再完成 embedding、融合和 DFlash 前向。

Target 验证后，我们用接受前缀、修正/bonus token 及对应的 Target hidden 推进 MTP 状态，缓存下一轮的预测表示。下一轮即可直接从 T1 head 开始。

6.2 Attention 适配：同一 backend，不同可见范围

我们继续使用 DFlash 已有的 FA3 和 CUDA Graph，并把新增 MTP 路径也接到 FA3 上。不过，两侧的可见范围不同：MTP 需要完整历史的 causal attention；DFlash 则读取相对 anchor 最近的 4096 个历史位置，以及按训练约定可见的七槽输入块。

DFlash 路径通过临时页表表达历史窗口与七槽块，不搬动持久 KV，不改变 RoPE 位置，也不将 anchor-relative 窗口替换成 query-relative 窗口。MTP 路径保留原 FA3 attention 算子，针对固定八槽输入在设备端准备 metadata，避免正常步骤依赖 CPU 长度回传。

6.3 KV 生命周期：持久历史、pending 与 scratch

图中以接受 T1、T2 后产生 bonus B 为例，展示 MTP 状态的推进与提交。

我们为 MTP 单独维护 KV，并额外保留 pending 槽位。原因是两侧的推进时序不同：MTP 可能已经处理了当前 anchor，而 Target 还没有。验证结束后，我们按接受结果分别更新两侧边界，只提交应该进入历史的状态。

为了让不同接受长度复用同一套图，我们给每个请求预留八个 MTP 推进槽位。有效行进入历史或下一轮 pending，多余行写入私有 scratch。提交哪些状态、取哪个 hidden 作为下一轮预测表示，都由有效行数决定，scratch 输出不参与后续预测。

6.4 图执行：优化新增阶段的准备与提交

我们按有效请求数预先捕获 CUDA Graph，让融合 GEMM 只计算实际需要的行。解码时通过设备端 staging 更新固定缓冲，再回放执行图。

随后，我们把 T1 head、候选写入、Target embedding 和融合算子合进一次图提交，减少 host 调度。这里只合并提交，不改变算子的依赖顺序、精度、argmax 或 TP 通信。

6.5 优化后的开销构成

经过设备端状态准备、固定布局和组合图优化，主要新增计算是一层 MTP decoder block 和选出 T1 的 LM head。MTP 仍包含全历史 causal attention、投影、归一化、MLP 和 TP 通信，其成本随上下文长度变化。

LM head 是后续的优化重点。 即使只生成 T1，标准 head 仍需进行全词表投影，读取大词表权重并计算 logits。

我们计划借鉴 EAGLE-4 的 Efficient LM Head，先用低秩 head 筛选候选，再用原始 head 精确重算；也会尝试起草侧 LM head 量化，降低权重读取与投影成本。Target 验证路径保持不变，优化效果将结合接受长度和吞吐评估。

8. 后续方向

DMTP 的一个局限，是它依赖原生 MTP 的首位预测能力。 如果 MTP 在某些场景下训练不够充分，它的首 token 接受率可能低于经过任务数据微调的 DFlash。这时，直接把首位交给 MTP 未必是更好的选择。我们还需要进一步探索这种差异，以及如何通过训练和两者的协作改善这些场景。

我们还想继续探索几个方向：

  • 自适应多步 MTP。 探索自适应选择 MTP 生成步数，再由 DFlash 并行续写。
  • 更强的验证方式。 在当前 target-only 验证基础上，探索 rejection sampling 与 block verify，评测其对接受长度、采样一致性及端到端吞吐的影响。
  • 统一MTP与DFlash的训练范式。 能否把两者放到同一个框架下，进一步理解首token接受率和后续位置衰减差异背后的原因？
  • 联合训练。 MTP不一定要冻结，也可以和DFlash一起训练，研究如何在保留首位优势的同时提升整个block的预测能力。
  • 多层MTP做block预测。 能否让多层MTP学习block预测，将已有的预训练能力与并行draft结合起来？
  • 更大的模型。 将 DMTP 扩展到更大规模的 Target，探索不同的 MTP–DFlash 组合，检验其在更大模型上的泛化能力与加速潜力。

DMTP 仍是一次初步探索。我们将继续分享更多模型与场景下的实验结果，相关论文与开源代码也将于近期公开。欢迎大家复现实验，分享不同模型、数据和任务上的发现，也欢迎参与训练方法与推理实现的改进，一起把这条路线探索得更清楚。

DMTP: A Better First Token for Block Drafting via MTP

Piggy Shen · October 2026 · Technical Blog

Speculative decoding is an important component of LLM inference infrastructure. DFlash demonstrates the potential of parallel candidate prediction, while DeepSeek has deployed DSpark in production and reported gains over MTP-1. Yet DFlash does not consistently outperform MTP on models with well-trained native MTP modules, such as GLM and Qwen, or on some conversation workloads.

Our evaluations and discussions with Domino author Jianuo Huang highlight complementary strengths: native MTP has higher first-token acceptance, particularly on OOD workloads, while DFlash generates a longer continuation in parallel. This motivates combining pretrained first-token prediction with parallel drafting.

Several approaches address the decline in acceptance at later positions within a DFlash-style block. We focus on a different question: can we improve the first draft token itself? Under prefix verification, rejecting that first candidate prevents the rest of the block from being committed. DMTP starts with a pretrained MTP prediction, then passes its hidden representation to DFlash for the continuation.

We introduce DMTP: pretrained MTP proposes the first token, and DFlash generates the continuation in parallel. Our main method is MTP-style token and hidden-state fusion: independently normalize the T1 embedding and its predicting MTP hidden, concatenate them, and project the pair into the T1 input position.

The key idea: let MTP start the block and DFlash continue it in parallel. The two models share both a concrete candidate and a predictive representation, while retaining their original backbones.

The Key Observations

  • Native MTP's first-token advantage is worth reusing. With the same Target and inputs, we observe higher first-token acceptance from MTP than DFlash. We therefore use MTP for T1 and DFlash for the remaining six parallel proposals.
  • Pass MTP's pretrained capability to DFlash through hidden states. We use MTP not only to generate T1, but also to fuse the hidden state that predicted it with its token embedding. DFlash can then use both the concrete candidate and features learned during MTP pretraining to predict the continuation in parallel.
  • The combination improves generation and complements existing optimizations. We obtain 9.25%–19.56% higher acceptance length across six workloads and 17.10%–23.75% higher end-to-end throughput across four workloads at B32, both relative to DFlash. DMTP changes how the two models cooperate and is orthogonal to optimizations within MTP or DFlash: stronger predictors, training methods, candidate-selection strategies, and inference kernels can be combined with this framework.

1. First-Token Acceptance and Parallel Drafting

Figure 1 compares DFlash and native MTP using the same target model. DFlash is trained on a mixture of tasks with 32K sequences; MTP uses the pretrained weights bundled with the same target.

Both arms use the same Qwen3.6-35B-A3B target and input set across Code, Math, MT-Bench, Agent, SWE and Long-horizon. DMTP itself uses MTP for T1 and DFlash for six parallel continuation candidates.

Figure 1. First-token acceptance across six workloads on Qwen3.6-35B-A3B at a generation temperature of 1.

On Code, first-position acceptance is 71.00% for DFlash and 82.32% for MTP.

We see extensive pretraining as an important source of MTP's first-token advantage. Native MTP learns alongside the target from much more data than our separately trained DFlash draft. That gives us a reason to preserve its first-token predictor rather than train a replacement.

2. DMTP: MTP Starts, DFlash Continues

The division of labor is straightforward:

MTP:     propose T1
DFlash:  condition on T1 and propose T2–T7 in one forward pass
Target:  verify seven candidates and commit the accepted prefix plus correction/bonus

Figure 2. Original DFlash (top) and DMTP (bottom). DMTP fuses the MTP hidden that predicts T1 with its token embedding, then predicts T2–T7 in parallel. The original target-context-to-KV path is retained; the T1 embedding comes from a token lookup.

We chose this division of labor for three reasons.

Preserve first-token prediction. We freeze native MTP to retain its pretrained first-step capability and train the parallel continuation separately.

Shorten the prediction distance. Given T1, T2 becomes the first unknown token after the new anchor, from which DFlash predicts the continuation in parallel.

Transfer pretrained features. Alongside T1, we pass the MTP hidden that predicted it so DFlash can use those features to predict subsequent tokens.

Single-Step MTP Drafting

We use MTP only for T1 to control serial drafting cost. Additional MTP candidates require successive forward passes and token selection, whereas DFlash predicts the remaining six in one parallel pass.

3. MTP Hidden-State Integration and Ablations

We use MTP-style token and hidden-state fusion and compare alternative representation interfaces through ablations.

Let A=xaA = x_aA=xa​ be the pending target-produced token. Target context ends at xa−1x_{a-1}xa−1​. Native MTP consumes AAA and the preceding target hidden, producing the representation that predicts T1=xa+1T_1 = x_{a+1}T1​=xa+1​. No target hidden for AAA or T1T_1T1​ is required.

Fusion reads the MTP hidden that predicted T1, not one computed after consuming T1:

e~T1=Wf[RMS⁡e(eT1);RMS⁡m(hMTP)].\widetilde{\mathbf e}_{T_1}=W_f\left[\operatorname{RMS}_e(\mathbf e_{T_1});\operatorname{RMS}_m(\mathbf h_{\mathrm{MTP}})\right].eT1​​=Wf​[RMSe​(eT1​​);RMSm​(hMTP​)].

Each 2048-dimensional input has its own learned RMSNorm, followed by a 4096→2048 linear projection. The input is [T1,MASK×6], with only the T1 embedding replaced. All six MASK embeddings, the original prediction head, and the target-context FC→KV path stay unchanged; no MTP KV slot is added.

The MTP-Style Fusion Interface

We follow native MTP's normalization-and-projection pattern, with separately trained fusion parameters. E(T1) identifies the candidate, MTP hidden provides predictive features, and all six MASK queries attend to the fused T1.

The change is confined to T1's input. Historical features, the target-context pathway, the DFlash backbone, and the proposal budget remain unchanged.

Single-Anchor Conditioning

One anchor, seven proposals. T1 is the only DFlash anchor; DFlash predicts T2–T7 in parallel. T1 can still be rejected. The seven proposals are T1–T7.

MTP still consumes A and produces T1 and its predicting hidden state; DFlash receives only the fused T1 and six MASKs. Target context ends before A, with no additional Target forward required.

Two anchors means retaining both the original anchor A and the MTP proposal T1 before the MASK positions. The input is [A,T1,MASK×6], rather than the single-anchor [T1,MASK×6]. The extra E(A) lets MASK queries directly access the original anchor's token embedding through attention. A has already been emitted and is not a new proposal.

We choose the single-anchor layout for similar performance with fewer changes: replace the original anchor with T1 and retain the anchor-plus-MASK structure. MASK embeddings, parallel prediction, and the original output head stay unchanged, making continued fine-tuning of an existing DFlash straightforward.

Figure 3a. Seven input slots, seven proposals: T1 comes from MTP and T2–T7 come from DFlash. The known T1 slot receives no draft prediction loss.

  • Original DFlash: single-anchor external baseline with [A,MASK×7]; DFlash proposes all seven candidates.
  • Candidate-conditioned single-anchor drafting: [T1,MASK×6], without additional MTP state injection; original target context remains available.
  • Hidden-state residual at the first candidate: project MTP hidden through a low-rank network and add the residual only to the T1 embedding; all six mask inputs stay unchanged.
  • MTP-style token and hidden-state fusion (main method): independently normalize and concatenate MTP hidden and E(T1), then project to replace only the T1 embedding.

Supplementary controls are a hidden-state residual at six mask positions, target and MTP context fusion, and MTP-only context. Context fusion concatenates five target feature streams and aligned MTP features, then projects 6H→H. These representation-interface comparisons all use T1 as their only anchor.

Compatibility with Existing Drafting Methods

We retain DFlash's backbone, output head, and target-context interface. With a compatible configuration, we can continue fine-tuning existing DFlash weights, add the T1 fusion module, and supervise the six continuation positions using [T1,MASK×6]. Target and MTP remain frozen.

This interface is orthogonal to optimizations within MTP or DFlash and can incorporate stronger predictors, training methods, path selectors, and inference kernels.

Why Preserve Pretrained MTP?

We also tried repurposing MTP layers for DFlash-style parallel prediction, but saw first-position performance affected and limited convergence gains. We therefore chose to freeze pretrained MTP and train parallel continuation around its T1 proposal.

4. Training DMTP

We use Qwen3.6-35B-A3B with 32K training contexts and approximately 250K records, predominantly from Agent and Long-horizon scenarios. We use MT-Bench as an out-of-distribution (OOD) evaluation to examine generalization beyond the training distribution.

Training follows three steps:

  1. Extract frozen features. Target processes the training sequence. At each block boundary, MTP consumes A and the preceding target hidden to obtain the representation for predicting T1. DFlash context uses only target features before A.
  2. Build the draft input. Use [T1,MASK×6] with the dataset's T1. Independently normalize E(T1) and its predicting MTP hidden, concatenate, and project to replace the T1 embedding. All six MASK embeddings remain unchanged.
  3. Optimize the continuation. DFlash learns T2–T7 with the original position-decayed CE objective. Target and MTP stay frozen; only DFlash and the T1 fusion module are updated. The known T1 input slot receives no draft prediction loss.

We use GT T1 during training and MTP-generated T1 during inference, so that train–inference difference remains. We keep the hidden-state timing consistent: both use the MTP representation that predicts T1, not the hidden obtained after consuming it.

5. Inference: MTP First, DFlash Second

Each generation round follows the order in Figure 2:

  1. MTP proposes T1. Read the available target hidden and consume pending token A. Keep both the selected T1 and the MTP hidden that predicted it.
  2. DFlash predicts T2–T7. Form [T1,MASK×6], fuse E(T1) with its predicting MTP hidden, replace only the T1 embedding, and run one parallel DFlash forward.
  3. Target verifies the block. Verify T1–T7 together, commit the accepted prefix and correction/bonus token, then advance to the next round.

We use target-only verification throughout these experiments. We check candidates token by token against Target samples and accept the consecutive matching prefix. We have not yet integrated rejection sampling or block verify; we plan to compare their effects on acceptance length and throughput.

The runtime keeps MTP and DFlash state separate, commits only accepted history, and rolls back rejected candidates.

The additional computation consists of an MTP forward, its first-token LM head, two normalizations, and a T1 fusion projection. The target-context pathway remains unchanged; DFlash uses seven input slots: T1 and six MASKs.

We next focus on state updates, execution scheduling, and CUDA Graph coverage to reduce the handoff cost between MTP and DFlash.

6. Inference Implementation and Systems Optimizations

We retain the seven-candidate budget and Target's verification rules, and focus our systems changes on MTP state advancement and T1 preparation.

6.1 Separating Prediction from State Advancement

The dashed frame groups the T1 head, embedding, and fusion in one CUDA Graph; the dashed arrow connects adjacent rounds.

Prefill initializes all three models' states. Each steady-state round selects T1 from the cached MTP hidden, then runs embedding, fusion, and the DFlash forward.

After Target verification, we advance MTP state using the accepted prefix, correction/bonus token, and corresponding Target hidden states. We cache the next prediction representation so the following round starts directly at the T1 head.

6.2 Attention: One Backend, Different Visibility Rules

We keep DFlash's existing FA3 and CUDA Graph support and use FA3 for the added MTP path as well. The two paths need different visibility rules: MTP reads full history causally, while DFlash reads the last 4096 positions relative to the anchor and its seven-slot block with the visibility used in training.

Temporary DFlash page tables express this visibility without moving persistent KV, changing RoPE positions, or replacing the anchor-relative window with a query-relative one. The MTP path retains the native FA3 operator and prepares fixed-eight-slot metadata on device, avoiding CPU length transfers on normal steps.

6.3 KV Lifetime: Persistent History, Pending, and Scratch

MTP state advancement and commit, illustrated with T1 and T2 accepted and bonus B produced.

We maintain a separate KV cache for MTP, with an additional pending slot, because the two models advance at different times: MTP may have processed the current anchor while Target has not. After verification, we update their boundaries separately and commit only the states that belong in history.

We reserve eight MTP advancement slots per request so different acceptance lengths can reuse the same graphs. Valid rows enter history or the next pending slot; extra rows go to private scratch. The valid-row count determines what we commit and which hidden state predicts the next T1. Scratch outputs do not enter subsequent predictions.

6.4 Graph Execution: Preparation and Submission

We pre-capture CUDA Graphs for exact request counts so the fusion GEMM computes only the active rows. During decoding, we update fixed buffers through device staging and replay the graph.

We then combine the T1 head, candidate write, Target embedding, and fusion into one graph submission to reduce host scheduling. We merge submissions without changing operator dependencies, precision, argmax behavior, or TP communication.

6.5 Cost Structure After Optimization

After device-side preparation, fixed layouts, and combined graph execution, the main added computation is one MTP decoder block and the LM head that selects T1. The block includes full-history causal attention, projections, normalization, MLP, and TP communication, so its cost varies with context length.

The LM head is a priority for further optimization. Even for a single T1, a standard head reads the large vocabulary matrix and computes full-vocabulary logits.

We plan to explore EAGLE-4's Efficient LM Head, using a low-rank head to shortlist candidates before exact rescoring, as well as drafting-side head quantization to reduce weight traffic and projection cost. Target verification stays unchanged; we will evaluate both acceptance length and throughput.

8. Future Directions

One limitation of DMTP is its reliance on native MTP's first-token prediction. When MTP is insufficiently trained for a particular setting, its first-token acceptance can be lower than that of a DFlash model fine-tuned on relevant task data. Delegating the first token to MTP may then be the weaker choice. We want to better understand this gap and explore how training and cooperation between the two models can improve those settings.

Beyond the current target-only verifier, we plan to explore rejection sampling and block verify, evaluating acceptance length, sampling consistency, and end-to-end throughput.

There are several directions we would like to explore:

  • Adaptive multi-step MTP. Explore adaptively choosing the number of MTP steps before parallel DFlash continuation.
  • A unified MTP–DFlash formulation. Can we train both within one framework and better understand why their first-token acceptance and later-position decay differ?
  • Joint training. MTP does not have to stay frozen. We can train it together with DFlash and study how to improve block prediction while preserving its first-token strength.
  • Multi-layer MTP for block prediction. Can multiple MTP layers learn to predict a block, combining pretrained MTP capabilities with parallel drafting?
  • Larger models. Extend DMTP to larger target models and explore different MTP–DFlash combinations to evaluate its generalization and acceleration potential at scale.

DMTP is still an initial exploration. We will share results across more models and settings, with the paper and open-source code to follow soon. We welcome reproductions, findings from different models and tasks, and contributions to both training methods and inference implementations. We hope to explore this direction together with the community.
